# Шлюз моделей СПАС

Локальный шлюз предоставляет агентам СПАС единый доступ к моделям. Транспорт
и авторизация принадлежат адаптерам, выбор аккаунтов и обновление данных доступа —
Auth Manager.

## Адаптеры

| Backend | Авторизация | Запрос | Лимиты |
| --- | --- | --- | --- |
| `codex_subscription` | Sign in with ChatGPT, OAuth + PKCE | Responses API | Подписка ChatGPT |
| `claude_subscription` | Официальный `claude auth login` | `claude -p` или Python Agent SDK | Подписка Claude |
| `openai_compatible` | API-ключ либо явно выбранный доступ без ключа | Chat Completions или Responses | Квота выбранного сервиса / ресурсы сервера |
| `openai_api` | API-ключ | Responses по умолчанию; настройки совместимы с универсальным API | Совместимость с прежней конфигурацией |
| `remote_inference` | Ключ своего сервера либо без ключа | Chat Completions API | Ресурсы Colab / своего runtime |
| `colab_managed` | OAuth приложения Colab CLI + PKCE | Приватный Transformers сервер через Jupyter | Runtime и квота Colab |

Подписочные адаптеры не используют API-ключи из окружения и не переключают способ
оплаты самостоятельно. Резервное подключение используется только при явно заданном
маршруте. API-подключения используют отдельные аккаунты и не зависят от подписок.

Официальные источники, проверенные 9 октября 2026 года:

- [Sign in with ChatGPT: регистрация и вход](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).
- [Доступные модели и Responses API](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference).
- [Preview-ограничения](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).
- [Обновление и отзыв OAuth-сессий](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).
- [Ошибки и восстановление ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).
- [Claude SDK/CLI с подпиской, обновление от 7 октября](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan).
- [Claude CLI reference](https://code.claude.com/docs/en/cli-reference) и [Python SDK reference](https://code.claude.com/docs/en/agent-sdk/python).

Документация описывает способы интеграции; наличие доступа у конкретного аккаунта
подтверждается командой `probe`. В [обзоре Claude SDK](https://code.claude.com/docs/en/agent-sdk/overview)
сохраняется отдельная оговорка о предоставлении claude.ai login в продуктах третьих
лиц. Локальная работа с собственной подпиской и условия распространения продукта
должны рассматриваться отдельно. Эта реализация запускается локально под аккаунтом
пользователя. Для коммерческого/размещённого сервиса нужно проверить применимые
условия провайдера; публикация такого сервиса не входит в текущую реализацию.

## Структура

```text
llm/gateway/
├── main.py                 # FastAPI и сборка зависимостей
├── config.py               # TOML, backend'ы и маршруты
├── cli.py                  # spas-llm
├── tui.py                  # интерактивное терминальное меню
├── api/                    # completions, административные endpoints и reload
├── core/                   # контракты, capabilities, registry, router, журнал
├── auth/                   # vault, ChatGPT/Google OAuth, Auth Manager и Claude
├── colab/                  # создание runtime, установка модели и Jupyter транспорт
├── providers/              # единый интерфейс и отдельные адаптеры
└── Dockerfile
```

`LLMProvider` реализует `generate`, `stream`, `health`, `list_models`. Нормализованный
поток содержит текстовые события и одно событие завершения с usage. Успех фиксируется
после завершения транспорта и подтверждения результата провайдером. Оборванный
поток не становится успешным ответом.

## Установка и первые независимые проверки

Требуется Linux с Docker Engine и плагином Docker Compose. Python, зависимости
Gateway и официальный Claude Code из `claude-agent-sdk` входят в общий образ.
Устанавливать Python, uv или Claude Code на хосте не требуется.

Из основной директории проекта:

```bash
docker compose up --build -d
docker compose ps
curl http://127.0.0.1:8008/health
```

Compose собирает образ с версиями зависимостей из `uv.lock`. Сервис `gateway-init`
создаёт конфигурацию, ключи Gateway и шифрованное хранилище, затем завершается.
Сервис `gateway` запускается после успешной инициализации. Повторный запуск
сохраняет существующие настройки. Сервер доступен на `127.0.0.1:8008`.

Конфигурация `gateway.toml`, ключи и аккаунты хранятся в именованном томе
`spas_llm-state`, внутри контейнера — в `/home/spas/.local/state/spas/llm`.
Пример конфигурации: [llm-gateway.example.toml](../config/llm-gateway.example.toml).
Аккаунты, модели, маршруты и проверки настраиваются через терминальный интерфейс СПАС:

```bash
docker compose run --rm tui
```

Сервис `tui` использует тот же образ и том, но запускается только по команде.
На Linux он использует сеть хоста: это позволяет браузеру на той же машине
обратиться к OAuth callback на `127.0.0.1`. Откройте напечатанную ссылку в браузере
хоста; браузер внутри контейнера не требуется. Если Docker работает на удалённой
машине, одного открытия ссылки на своём компьютере недостаточно: callback
должен попасть на loopback машины, где выполняется вход.

### ChatGPT

В интерфейсе СПАС откройте **Подписки ChatGPT и Claude → Аккаунты и вход → Подключить аккаунт ChatGPT или Claude → ChatGPT**, задайте имя аккаунта
(по умолчанию `chatgpt-main`) и откройте напечатанную ссылку в браузере хоста.
Затем **Подписки ChatGPT и Claude → Модели и подключения → Каталог моделей → ChatGPT** покажет модели аккаунта. Выбранная модель
задаётся через **Подписки ChatGPT и Claude → Модели и подключения → Настроить подключение → chatgpt**. Для реального запроса откройте
**Главная → Тестирование → chatgpt**, введите текст и получите потоковый ответ.

Команда запускает HTTP callback на `127.0.0.1` до открытия системного браузера.
Начальная регистрация получает выданный `client_id`; повторный вход использует
сохранённый ID и стабильный ID хоста. Проверяются state, PKCE, подпись JWT через
JWKS, issuer, audience, срок действия, nonce и совпадение выбранной учётной записи.
Отсутствие разрешения `chatgpt.tokens.use.direct` сохраняет учётную запись, но
запрещает inference. Повторное согласие запрашивается только при выборе соответствующего пункта
во время входа в разделе «Подписки ChatGPT и Claude → Аккаунты и вход».

Каждый HTTP-запрос отправляется на официальный `https://api.openai.com/v1/responses`
с `store=false`, `stream=true`. Внешний `stream=false` означает сбор этого потока
Gateway'ем. История передаётся целиком, системные/developer-инструкции объединяются
в `instructions` в порядке появления. Успех требует `response.completed`.

Каталог моделей читается с OAuth-токеном выбранного аккаунта: используются `slug`
и `display_name` из видимых записей. Исходный `gpt-6.1-sol` — пример из официальной
документации; проверьте его доступность своему аккаунту перед запуском.

Обновление токенов выполняется перед истечением срока; операции сериализуются
для одного аккаунта, включая разные процессы. Ротация сохраняет новый refresh
token. Терминальная ошибка refresh очищает токены, сохраняя регистрацию для входа.
Временная ошибка сети сохраняет credentials. При выходе выполняется попытка
отзыва сессии; если её подтвердить не удалось, CLI явно сообщает об этом.

### Claude

В интерфейсе СПАС откройте **Подписки ChatGPT и Claude → Аккаунты и вход → Подключить аккаунт ChatGPT или Claude → Claude** и используйте аккаунт
`claude-main` либо своё имя. После входа откройте **Главная → Тестирование → claude**,
введите текст — ответ начнёт поступать по мере генерации.

Для импорта существующего Linux-профиля предоставьте TUI каталог только для чтения:

```bash
docker compose run --rm --volume "$HOME/.claude:/import/claude:ro" tui
```

Выберите **Подписки ChatGPT и Claude → Аккаунты и вход → Импортировать профиль Claude**, имя аккаунта и каталог `/import/claude`.

Импорт не изменяет исходные файлы. Для нескольких аккаунтов используйте разные
имена и отдельный `login`. При `authMethod=api_key`, `api_key_helper` или
`third_party` подписочный адаптер отклоняет профиль.

**Используется `--safe-mode`, а не `--bare`.** В установленном Claude Code 2.1.269
help для `--bare` прямо указывает, что OAuth/keychain не читаются. Для обычного
запроса отключаются все инструменты (`--tools ""`, `--disallowedTools "*"`), MCP,
настройки и сохранение сессий. `--safe-mode` отключает пользовательские hooks,
плагины, skills и загрузку CLAUDE.md, сохраняя обычную авторизацию. Gateway удаляет
из окружения runtime API-ключи, OAuth override, переключатели сторонних провайдеров
и свои секреты; повторные запросы CLI на ошибках отключены.

Для Python SDK откройте **Подписки ChatGPT и Claude → Модели и подключения → Настроить подключение → claude** и выберите транспорт
`sdk`. CLI и SDK входят в один образ; дополнительная установка не требуется.
После сохранения настройка используется проверками TUI сразу, а HTTP-сервером —
после перезапуска Gateway.

SDK использует тот же официальный runtime, отключённые инструменты и отдельную
сессию на запрос. Сессии разных агентов не разделяют контекст. `/chat/completions`
не хранит диалоги; вызывающий агент передаёт историю. Для CLI/SDK многосообщная
история сериализуется как JSON-диалог с инструкцией продолжить последний запрос;
это адаптация текстового интерфейса Claude Code, а не native Messages API.
Текущая реализация создаёт runtime на каждый запрос. Постоянный пул SDK-сессий
потребует отдельного контракта идентификации и жизненного цикла сессий агентов.
Каталог Claude показывает настроенный alias, не выдаёт его за проверенный список
доступа подписки. OAuth-токены не передаются в Messages API.

`health` проверяет сохранённую авторизацию, но не расходует квоту на inference.
Сохранённый вход может быть недействителен: `probe` распознаёт это и сохраняет
`REAUTH_REQUIRED`. `last_success_at` сообщает время последнего успешного запроса.

### Произвольный OpenAI-совместимый API

В интерфейсе СПАС откройте **API моделей → Добавить подключение**.
Один сценарий сохраняет подключение, авторизацию и имя модели в шлюзе:

1. Задайте название подключения. Профиль для хранения ключа создаётся автоматически.
2. Введите базовый URL API. Адрес без пути получает `/v1`; явно указанный путь
   сохраняется: `https://host/proxy/api/v3/` → `https://host/proxy/api/v3`.
   Можно вставить полный адрес `/chat/completions`, `/responses`, `/decisions`
   или `/systemone`: формат и базовый путь определятся автоматически.
3. Выберите **Chat Completions** или **Responses** и укажите ID модели сервиса.
4. Для текстовой модели потоковый ответ включён по умолчанию.
   Настройки совместимости, статистика токенов, JSON-ответы, время ожидания
   и параллельность доступны отдельно: **подключение → Расширенные параметры**.
   Там же задаётся поддержка Box для модели решений.
5. Выберите API-ключ (скрытый ввод) либо **Без ключа** для локального сервера.
   При редактировании прежнего URL можно оставить сохранённую авторизацию.
6. Задайте свободное имя модели в шлюзе, например `local-default`.
7. Нажмите **Применить настройки** в меню API. Если сервер не запущен,
   настройки сохраняются и будут прочитаны при его запуске.
   Замена ключа или способа доступа также вступает в силу после применения настроек.

Выберите подключение в списке, чтобы изменить его настройки, выбрать модель из
каталога `/models` или вручную, выполнить пинг, отключить авторизацию или удалить
подключение. При переходе от модели решений к текстовой выберите формат
**Chat Completions** или **Responses**: адрес запроса обновится вместе с типом модели.
Реальные запросы отправляются из **Главная → Тестирование**. Если сервис не предоставляет
`/models`, задайте ID вручную и используйте проверочный запрос: ошибка каталога
не запрещает генерацию. Проверочные запросы расходуют квоту выбранного сервиса.
Удаление подключения убирает его из маршрутов, удаляя опустевшие маршруты.
Сохранённый аккаунт остаётся доступен для других подключений; очистка его ключа —
отдельное действие **Удалить сохранённый доступ**.

API-ключи хранятся в зашифрованном vault, отдельно от TOML. Переходы по HTTP
redirect отключены. Старые `provider = "openai_api"` и их аккаунты продолжают
работать: URL по умолчанию `https://api.openai.com/v1`, формат — Responses.
Новые подключения используют `provider = "openai_compatible"` и Chat Completions
по умолчанию. Полный URL с окончанием `/decisions` или `/systemone` автоматически
определяет Decision-протокол, даже если раньше был выбран Responses. Имена
Mercury Decide и Jev также распознаются автоматически; для других моделей явно
выберите формат Decision. Примеры настройки — в `config/llm-gateway.example.toml`.

Для конфигурации вручную сохраните ключ через
`spas-llm api-key ACCOUNT --provider openai_compatible` либо явно разрешите работу
без ключа: `spas-llm api-key ACCOUNT --provider openai_compatible --no-auth`.
Ключ не передаётся аргументом командной строки.

Форматы запросов сверены с официальной OpenAI Docs:
[Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)
и [Responses streaming events](https://developers.openai.com/api/reference/resources/responses/streaming-events).
Поддерживается текстовый контракт Gateway; совместимость конкретного сервиса
подтверждается проверочным запросом. Инструменты и мультимодальные входы
в этот контракт не входят.

Чтобы использовать API как резерв, в **Настройки шлюза → Маршруты и резервные подключения** задайте логическую
модель и список подключений по порядку, например `chatgpt,custom-api`, а также
ошибки, при которых разрешён резервный маршрут.

### Модели решений: Choice, Noul, Score и Box

Для `inception/mercury-decide:free` через OpenRouter укажите
`https://openrouter.ai/api/alpha/decisions` и формат `decisions`. Сохранённое
подключение с таким полным URL распознаётся без пересоздания и повторного ввода
ключа. Каталог читается отдельно, с `/api/v1/models?output_modalities=decisions`.
Для сервиса с совместимым System One используйте `api_format = "systemone"` и
базовый URL `/v1` либо полный URL `/v1/systemone`.

Откройте **Главная → Тестирование → подключение**. Для Decision-модели
последовательно выберите режим, введите состояние (`state`), вопрос
и критерии. После последнего ввода запрос сразу отправляется модели.
Для Choice перечислите варианты через `;`, для Score — уровни от низкого
к высокому через `;`, для Noul — необязательные описания «да» и «нет».
Для Box на шаге состояния также укажите путь к изображению.

| Режим | Критерии | Результат |
| --- | --- | --- |
| Choice | Имена вариантов и необязательные описания | Выбранный вариант, распределение вероятностей и уверенность |
| Noul | Вопрос и необязательные описания «да» / «нет» | Вероятность положительного ответа от 0 до 1 |
| Score | Описания уровней от низкого к высокому | Средневзвешенный индекс уровня, распределение и уверенность |
| Box | Описание объекта на изображении | Нормированные координаты `top`, `bottom`, `left`, `right` и уверенность |

Шкала Score начинается с 0, ответ может быть дробным. Форма предлагает 2–10
описанных уровней; JSON-контракт также допускает один уровень для сервисов,
которые его принимают. Choice допускает 1–255 вариантов; конкретная модель
может устанавливать более строгие ограничения. Вероятности сравнивают заданные
варианты, а уверенность не означает вероятность правильного ответа.

В [документации OpenRouter по Jev](https://openrouter.ai/docs/guides/community/jev)
описаны все четыре примитива. **Mercury Decide поддерживает Choice, Noul и Score**;
Box документирован для Jev 1.14 и `~typesafe/jev-latest`. Форма предлагает только поддерживаемые моделью режимы; Gateway также
проверяет доступность Box до обращения к модели.
Для другого совместимого сервиса поддержку Box можно указать в форме подключения
или через `decision_box = true` в TOML. Сам выбор модели в каталоге сбрасывает
прежнее переопределение Box и заново определяет возможности модели.

Контракт HTTP Gateway — `POST /v1/decisions` с `model`, `state` и `questions`.
Состояние может быть строкой, объектом или массивом. Вопросы содержат `type`,
`instructions` и, кроме Box, `criteria`. Дополнительные поля и `stream`
отклоняются. Ответ содержит `answers` под исходными ID вопросов и `usage`,
если провайдер его вернул. Проверяются типы, варианты, вероятности, диапазоны
Score и координаты Box. Контекст и ответы не записываются в журнал запросов.

Пример с тремя вопросами: [decision-systemone.example.json](../config/decision-systemone.example.json).

```bash
spas-llm decide Jev-like --input config/decision-systemone.example.json --pretty
```

Без `--pretty` CLI выводит JSON. В JSON состояния для OpenRouter изображения
передаются верхнеуровневыми частями `image_url` с base64 data URL; текст рядом с
ними — обычными строками. Для Box форма принимает один PNG, JPEG или WebP до 10 МиБ;
весь запрос ограничен 20 МиБ. Через JSON API доступны несколько изображений. Лимиты конкретного сервиса
могут быть ниже. Box требует изображения в состоянии. Формат взят из
[Decisions API](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request),
[мультимодального руководства](https://openrouter.ai/docs/guides/community/multimodal-decisions)
и [документации Mercury Decide](https://docs.inceptionlabs.ai/capabilities/decisions).

Старый контракт Nimble `context` + `schema` сохранён. Форма проверки работает
также с локальным Nimble через Colab: Choice и Noul преобразуются в enum/boolean,
Score — в enum уровней с вычислением ожидаемого индекса по вероятностям.
Для такого Score confidence вычисляется Gateway как единица минус
нормированная энтропия. Изображения и Box локальный Nimble не поддерживает.
Все элементы резервного маршрута должны поддерживать выбранный тип ответа.

## Серверы Google Colab

### Подключение и запуск модели

Откройте **Google Colab**. Раздел показывает настроенные подключения, модель,
GPU, сохранённое состояние и маршруты. Выберите своё подключение, чтобы открыть
его настройки и управление. **Esc** возвращает к списку подключений.

Основной путь использует [официальный Google Colab CLI](https://github.com/googlecolab/google-colab-cli)
версии 0.7.4, включённый в Docker-образ. Собственный Google проект, одобрение
Colab API beta и создание Desktop OAuth-клиента не требуются: используется
OAuth-клиент, поставляемый с приложением Colab. Токены остаются в зашифрованном
хранилище СПАС; CLI не записывает отдельный открытый `token.json`.

1. **Аккаунты Google → Подключить аккаунт Google**.
   Задайте имя профиля, например `google-main`, откройте напечатанную ссылку
   в браузере и выдайте разрешения приложению. Скопируйте показанный Google код
   в скрытое поле TUI. Используется зарегистрированная HTTPS-страница Google
   для удалённого входа, PKCE и проверенный ID token с nonce. Это работает
   и в контейнере, без перенаправления на localhost. Refresh token обновляется
   с блокировкой профиля между процессами.
2. **Аккаунты Google → Проверить подключение к Colab**.
   Выполняется запрос списка сессий без создания runtime.
3. Для пользователей с уже одобренным **Colab API beta** доступны дополнительные
   пункты настройки собственного Desktop OAuth-клиента и входа через него.
   Для этого отдельного пути сохраняются [требования REST API](https://developers.google.com/colab/api/reference/rest).
4. **Добавить подключение** для нового сервера; для существующего выберите
   **Открыть <имя> → Настройки подключения**.
   Создайте подключение, выберите Google-профиль и поддерживаемый CPU/GPU,
   например T4. В режиме CLI доступность GPU и увеличенной RAM проверяется
   при запуске по квоте аккаунта и наличию ресурсов; каталог не гарантирует
   выделение выбранного ускорителя. Укажите репозиторий модели на Hugging Face.
   Ревизия, точность, контекст, длина ответа, порт и время ожидания
   вынесены в **Расширенные параметры**; обычная форма использует сохранённые
   значения или значения по умолчанию. Для закрытой/gated модели
   введите Hugging Face token в скрытом поле; сначала получите доступ к модели
   у её владельца. Enter сохраняет токен, `-` удаляет его.
5. **Открыть <имя> → Запустить модель**.
   СПАС создаёт среду Colab, устанавливает зависимости в отдельное окружение,
   скачивает safetensors и tokenizer, запускает сервер и загружает модель.
   Для установки используются `venv --without-pip` и pip исходного Colab
   через `--python`: отсутствие `ensurepip` в образе Colab не препятствует установке.
   Затем выполняет короткую настоящую генерацию через транспорт Gateway и
   применяет маршрут модели без перезапуска контейнера.
   Экран обновляется в стиле `docker compose`: отдельные строки для выделения
   runtime, подключения, окружения Python, зависимостей, PyTorch, скачивания,
   загрузки модели, проверочного запроса и применения маршрута. Для Nimble
   дополнительно видны scorer, проверка контракта и базовые веса;
   слияние LoRA отмечено как пропущенное, адаптер подключается при загрузке сервера.
   У каждого шага отображаются состояние и длительность; сверху — общее время
   запуска. Таймеры продолжают обновляться, даже когда runtime не присылает событий.
   При скачивании показаны прогресс-бар, процент, объём данных, скорость и
   оценка оставшегося времени. Если Hub не сообщает байты (например, все файлы
   уже в кэше), используется счётчик файлов. Объём может уточняться по мере
   получения метаданных следующих файлов. Неиспользуемые шаги отмечаются как
   пропущенные. При ошибке или Ctrl+C итоговые статусы и время остаются на экране.
   Скачивание весов и базовой модели Nimble защищено watchdog: по умолчанию
   после 180 секунд без прироста байтов или числа файлов зависшая попытка
   завершается, затем скачивание возобновляется с сохранённым кэшем Hugging Face.
   Максимум — три попытки, паузы между ними — 5 и 10 секунд. Повторяются также
   временные ошибки сети, HTTP 429/5xx и аварийное завершение загрузчика.
   Ошибки доступа, неверный репозиторий/ревизия и нехватка места завершают операцию.
   Номер попытки, причина повтора и отсчёт паузы отображаются в статусе запуска.
   В расширенных параметрах можно задать время ожидания прогресса, число попыток и начальную паузу
   (`download_stall_timeout`, `download_max_attempts`, `download_retry_backoff`).
   Общий лимит установки и скачивания по-прежнему ограничивает полный запуск;
   ретраи не продлевают его. Ctrl+C останавливает также дочерний загрузчик.
6. **Главная → Тестирование → подключение Colab** отправляет реальный запрос.
   В меню подключения **Пинг и состояние модели** и
   **Загруженные модели** проверяют доступность без генерации.

Пример чат-модели в форме — `Qwen/Qwen2.5-1.5B-Instruct`. В режиме chat поддерживаются модели
`AutoModelForCausalLM`, встроенные в установленную версию Transformers, с
safetensors и chat template. Выполнение кода из репозитория отключено.
Точность: auto, float16, bfloat16, float32; auto учитывает CPU/CUDA и поддержку
bfloat16. TPU и загрузчики GGUF/произвольного Python-кода в этот backend не входят.
Размер модели должен помещаться в память выбранного runtime.

### Терминал Colab

В меню **Google Colab → Открыть <имя> → Открыть терминал Colab** можно работать
с оболочкой уже созданного runtime, в том числе после ошибки установки модели.
CLI для того же подключения:

```bash
spas-llm colab-terminal colab-gpu
```

Требуется интерактивный TTY; в Docker используйте `docker compose run --rm tui`.
Ввод, вывод, Ctrl+C и размеры окна передаются через Jupyter terminal WebSocket

Терминал не создаёт runtime и не запускает модель. Это локальный инструмент

Протокол использует [Jupyter Terminal API](https://jupyter-server.readthedocs.io/en/latest/developers/rest-api.html).

### Модели решений Jev-like: Nimble

Укажите `bespokelabs/Bespoke-Nimble-9B` в форме Colab. Тип `auto` распознаёт
семейство `bespokelabs/Bespoke-Nimble-*`; для другого совместимого репозитория
выберите `nimble`. Тип сохраняется и в настройках runtime, и в backend как
`model_kind`. Обычные чат-модели используют `chat`.

Nimble оценивает логиты заданных кандидатов и возвращает типизированные решения
без текстовой генерации. Используется [официальный CUDA scorer Bespoke Labs](https://github.com/bespokelabsai/nimble)
с закреплённым commit `dcfdbd9a64f0d869f658d7a72f1beaee32737773`.
Проверяется `schema_config.json` и хеши реализации промптов. При загрузке LoRA
скачивается базовая модель с ревизией из контракта. PEFT подключает адаптер
при загрузке без слияния всей модели в CPU RAM и без второй копии весов.
Tokenizer, контракт промптов и температура релиза берутся из исходного адаптера.
Код из Hugging Face репозитория не выполняется. Полный запуск проверяет решение
через тот же Jupyter-транспорт, которым пользуется Gateway.

Нужен CUDA runtime. По данным авторов, веса 9B без квантования занимают около
18 GB. Загрузчик ограничивает веса 80% свободной GPU памяти и 65% доступной CPU RAM;
остаток может выгружаться на диск runtime. Это позволяет использовать совместно
память T4 и CPU, но выгрузка весов замедляет inference. Выбирайте GPU, RAM, диск
и таймаут ответа с учётом размера модели и контекста. Квантование не реализовано.
Ошибки подготовки и запуска отличаются от ошибок скачивания. Подробности
неудачной подготовки сохраняются в приватном `setup-error.log`, ошибки сервера —
в `server.log` внутри `/content/spas/<deployment_id>/`. Токены из настроек
редактируются перед записью диагностического журнала подготовки.
Версия Transformers для Nimble — 5.17.0, PEFT — 0.21.0.

API Gateway: `POST /v1/decisions` с ключом агента, логическим `model`, текстовым
`context` и плоским `schema`. Поля имеют тип `enum` (уникальные строковые варианты)
или `boolean` и обязательное `description`; `choice_descriptions` задаёт критерии.
Gateway допускает до 64 полей и до 255 вариантов, но конкретный checkpoint может
иметь меньшие лимиты. Промпт целиком, включая схему, должен помещаться в лимит
модели; он не обрезается. Для текущего Nimble предел — 8192 токена.

```bash
spas-llm decide colab-gpu --input config/decision.example.json
```

В TUI используйте **Главная → Тестирование → подключение Colab**, затем
выберите Choice, Noul или Score и введите состояние, вопрос и критерии.
Пример HTTP-запроса:

```json
{
  "model": "colab-default",
  "context": "The payment service is unavailable.",
  "schema": {
    "incident": {"type": "boolean", "description": "Is a service unavailable?"}
  }
}
```

Ответ содержит `output` с выбранными значениями и `fields` с `value` и `scores`
для каждого варианта (`false`/`true` для boolean). Вероятности проверяются на
конечность, диапазон и сумму 1. Они относятся только к заданным вариантам;
пороги требуют проверки на ваших данных. Для оценки по шкале задайте её уровни
как enum и вычислите ожидаемый уровень по вероятностям.

Каталог `/v1/models` показывает `decisions=true`, `chat=false` для таких маршрутов.
Chat Completions и stream для них отклоняются. Маршрутизация, лимит параллельных
запросов, cooldown, таймауты и журнал применяются также к решениям; все элементы
резервного маршрута должны поддерживать решения. Журнал не сохраняет контекст,
схему или ответы. Для собственного сервера можно использовать `remote_inference`
с `model_kind="nimble"` и тем же контрактом `/v1/decisions`. Подключение к
Jev `/v1/systemone` настраивается как `openai_compatible` с форматом `systemone`.

Транспорт настраивается автоматически из proxy connection официального CLI
или `connectionInfo` REST API.
Gateway получает свежий краткоживущий proxy token перед подключением и открывает
Jupyter REST/WebSocket с заголовком `X-Colab-Runtime-Proxy-Token`. WebSocket
также передаёт proxy token в параметре соединения, как официальный CLI.
REST-контракт описан в
[контракте Google runtime](https://developers.google.com/colab/api/reference/rest/v1beta/runtimes).
Inference-сервер слушает только `127.0.0.1` внутри Colab и требует сгенерированный
ключ. Публичный туннель и ручной ввод URL не нужны. Переадресации не выполняются.
Агенты получают только текст, finish_reason и usage; доступ к выполнению кода,
файлам или инструментам Jupyter им не предоставляется.

Google OAuth credentials, настройки развёртывания, Hugging Face token и ключ
сервера хранятся в encrypted vault. Краткоживущий proxy token находится в памяти
транспорта. В `gateway.toml` сохраняются только backend `colab_managed`, имя
профиля, модель, таймаут и логический маршрут, например `colab-default`.
Backend поддерживает обычный ответ, SSE, usage, temperature и max_tokens;
tool calling и native JSON output отклоняются.

Этапы запуска: `CONFIGURED → ALLOCATING → INSTALLING → DOWNLOADING → STARTING
→ VERIFYING → READY`. Ошибка сохраняет `FAILED`, код и этап сбоя; отмена —
`INTERRUPTED`. Повторный запуск продолжает сохранённую операцию Google с тем же
requestId или использует уже выделенный runtime. Работающий сервер той же
конфигурации используется повторно; скачанные веса остаются в кэше runtime.
После исчезновения runtime статус становится `EXPIRED`; новый runtime создаётся
следующим явным запуском. Доступность GPU и длительность runtime зависят от Colab.

- **Остановить модель** завершает только процесс SPAS.
  Runtime и файлы остаются, GPU продолжает быть выделенным.
- **Завершить среду Colab** удаляет назначение Google вместе с
  файлами и кэшем. Профиль и маршрут остаются для следующего запуска.
- **Выйти из Google** отзывает локальную OAuth-сессию; сначала удалите runtime,
  если хотите освободить выделенные ресурсы.
- **Применить настройки** повторяет применение конфигурации, если
  после запуска Gateway был недоступен или изменяемое подключение было занято.

HTTP 429 сохраняет cooldown с Retry-After; успех параллельного запроса не
сбрасывает активный cooldown. Cooldown управляющего API разделяется всеми
подключениями одного Google-профиля. Резерв задаётся через **Настройки шлюза → Маршруты и резервные подключения**.
Автосоздание настраивается в **Открыть <имя> → Время работы и автозапуск**
и по умолчанию выключено. При включении работающий Gateway проверяет наличие VM
через управляющий API и создаёт замену после подтверждённого исчезновения,
затем устанавливает зависимости, загружает модель и проверяет inference.
Настройка применяется без перезапуска Gateway. Существующая VM не удаляется
из-за истечения оценочного таймера. Проверка выполняется примерно раз в 15 секунд;
при временных ошибках используется пауза 60–900 секунд, квоты Colab сохраняются.
Если VM уже выделена, но установка или проверка модели прервалась, следующая
попытка продолжает запуск на этой VM, используя сохранённый кэш весов.
Ошибки модели или авторизации приостанавливают автоматику до ручного запуска
или повторного включения настройки. Ручные остановка/удаление также ставят её
на паузу. Одно подключение не создаётся одновременно несколькими процессами Gateway.
Во время восстановления запросы агентов получают HTTP 503; могут использоваться
настроенные резервные маршруты. Запрос агента сам не создаёт VM.

В списке подключений, статусе и ходе запуска показано оценочное оставшееся время
VM. Базовый предел для оценки — 12 часов; его можно изменить в той же форме
(например, на 24 часа для подходящего тарифа). Это не обещанный Google срок:
[Colab меняет ограничения и может завершить VM раньше](https://research.google.com/colaboratory/faq.html).
Расчёт использует сохранённое время выделения VM, уточняемое по uptime runtime.
Если оно неизвестно, отображается «Неизвестно». Истечение proxy-токена не
используется как срок жизни VM: [официальный API](https://developers.google.com/colab/api/reference/rest/v1beta/runtimes)
описывает `connectionInfo.expireTime` именно как срок краткоживущего credential.
В API статуса данные находятся в `vm_time` и `auto_creation`; настройки в vault —
`vm_lifetime_hours` и `auto_create_runtime`. Остановка Gateway останавливает
фонового наблюдателя, но не удаляет VM.

Heartbeat для удержания простаивающей сессии не выполняется. Полный запуск требует работающего
Colab CLI либо отдельно настроенного Colab API beta. Автоматизация веб-интерфейса
и извлечение браузерных cookies не используются.

**Удалить подключение** сначала освобождает его runtime, затем удаляет backend
и ссылки на него в маршрутах. Другие элементы резервных маршрутов сохраняются.
Если освобождение runtime завершается ошибкой, подключение остаётся в списке.

## API и маршрутизация

```bash
docker compose up -d
docker compose run --rm tui
```

Сервер слушает `127.0.0.1:8008`. В TUI откройте **Настройки шлюза → Ключи доступа → Ключ агента**, чтобы получить внутренний ключ агента:

```bash
curl http://127.0.0.1:8008/v1/chat/completions \
  -H 'Authorization: Bearer YOUR_GATEWAY_KEY' \
  -H 'Content-Type: application/json' \
  -d '{"model":"codex-default","messages":[{"role":"system","content":"Ты диагностический агент СПАС."},{"role":"user","content":"Определи возможную причину HTTP 502."}],"stream":false}'
```

Поддерживаются `GET /v1/models`, `POST /v1/chat/completions`, обычный ответ и SSE
с текстовыми chunks, finish_reason и `[DONE]`. Для usage в SSE передайте
`stream_options: {"include_usage": true}`. Счётчики Claude включают cache read/write
в `prompt_tokens`; это метрика объёма, не стоимость или остаток квоты подписки.

`GET /v1/models` публикует логические имена и capabilities, доступные на всех
backend'ах маршрута. В первой версии подписки принимают только текстовые сообщения;
tool calling, native JSON output, temperature и ограничения выходных токенов
отклоняются с HTTP 400. `openai_api` отдельно принимает `temperature`, один из
`max_tokens`/`max_completion_tokens` (преобразуется в `max_output_tokens`) и
`response_format` типа `json_object`/`text`. Поддержка конкретной моделью остаётся
условием провайдера. Другие поля не игнорируются: они вызывают HTTP 400.

Маршрут — упорядоченный список backend'ов. По умолчанию fallback разрешён только
для `rate_limited` и `provider_unavailable`; список задаётся `fallback_on` в TOML.
Пример явного резерва:

```toml
[routes]
codex-default = ["chatgpt"]
sonnet-default = ["claude"]
diagnostic-default = ["chatgpt", "claude"]
```

После первого текстового события fallback запрещён и для внешнего `stream=false`.
Если ошибка случилась до потока, возвращается HTTP-ошибка. После начала SSE
передаётся событие `{"error":...}` без успешного finish_reason, затем `[DONE]`.
Ограничение провайдера приводит к `RATE_LIMITED`; используется его Retry-After,
а если он отсутствует — 60-секундная пауза защитного circuit breaker. Эта пауза
не объявляется сроком сброса подписочной квоты. Gateway не обходит ограничения
и не перебирает аккаунты вне настроенного маршрута.

## Аккаунты, ключи и TUI

```bash
docker compose run --rm tui
```

Главная страница сначала предлагает три способа работы с моделями:

- **Подписки ChatGPT и Claude** — вход и импорт профиля, состояния аккаунтов,
  каталог моделей, настройка подключений и пинг.
- **API моделей** — свой URL, необязательный ключ, Chat Completions или
  Responses, Decisions и System One, выбор модели, пинг и применение настроек.
  Оплата и квота зависят от сервиса.
- **Google Colab** — список подключений и управление выбранным сервером:
  Google-профиль, модель, runtime/GPU, запуск, пинг и остановка.

В каждом разделе отображаются только его подключения и аккаунты. Смешанные
маршруты с резервом из другого способа работы доступны в **Настройках шлюза**:
маршруты, внутренние ключи доступа и журнал запросов.
Главная страница показывает описание способов работы и количество подключений.
Отдельный пункт **Тестирование** объединяет все подключения из подписок, API
и Colab. Для LLM достаточно ввести текст: ответ поступает по мере генерации.
Если потоковый режим отключён, ответ выводится целиком.
Для моделей решений: режим → состояние → вопрос → критерии → ответ.
Пинг остаётся в разделе соответствующего подключения. Проверочные запросы
расходуют квоту выбранного сервиса.

Пункты меню выбираются **стрелками**, выбранный пункт подсвечивается.
**Enter** выбирает действие, **Esc** возвращает на предыдущий экран.
На главном экране **Esc** закрывает интерфейс.
Выбор аккаунтов, подключений, провайдеров и ответов «Да/Нет» работает так же.
В текстовых полях **Esc** отменяет текущую форму. **Ctrl+D** закрывает интерфейс
из любого меню или поля ввода, в том числе с заполненным значением.
**Ctrl+C** отменяет текущее действие; после операции или ошибки TUI остаётся
в выбранном разделе. Для первого подключения используйте порядок:
авторизация → настройка подключения → Главная → Тестирование.

Настройки сохраняются в общий том. Проверки TUI читают их сразу;
HTTP-сервер применяет Colab конфигурацию из TUI после полного запуска или выбора
«Применить настройки»; другие изменения можно применить тем же действием
или перезапуском Gateway. OAuth/Claude login выполняются локально,
без клиентских HTTP endpoint'ов для credentials.
Низкоуровневые команды CLI сохранены для автоматизации; для настройки они не требуются.

Административные read-only endpoints требуют отдельный ключ (раздел **Настройки шлюза → Ключи доступа → Ключ администратора**):
`/admin/accounts`, `/admin/providers`, `/admin/routing`, `/admin/logs`. Ключ агента
не даёт доступа к ним. Provider credentials не выдаются ни через один endpoint.
Можно задать `SPAS_GATEWAY_KEY` и `SPAS_GATEWAY_ADMIN_KEY` вместо ключей `init`;
значения должны различаться и иметь длину от 24 символов.
`POST /admin/reload` с ключом администратора применяет сохранённый TOML.
Неизменённые подключения сохраняют очереди и семафоры; изменение занятого backend
даёт 409, неверный TOML — 400. Ключ агента не разрешает reload.

Каждый аккаунт хранится отдельной записью Fernet с проверкой целостности. Каталоги
имеют права 0700, файлы credentials и ключа — 0600; запись атомарная. Ключ установки
находится в `master.key` либо задаётся `SPAS_CREDENTIAL_KEY` (Fernet key). При потере
ключа существующий vault не переинициализируется. Секретный ключ рядом с vault
защищает хранение при соблюдении прав доступа, а для отдельного управления ключом
используйте переменную окружения и системное хранилище секретов.

Claude-native `.credentials.json` и `.claude.json` хранятся внутри зашифрованной
записи. На время вызова они раскрываются в приватный временный каталог, предпочтительно
в `/dev/shm`; после окончания/отмены CLI каталог удаляется, обновлённая авторизация
снова шифруется. На системах без `/dev/shm` временные файлы создаются в системном
temp с правами доступа; это runtime-копия credentials. Исходный импортируемый
профиль остаётся в формате, которым управляет Claude Code.

Состояния аккаунта: `CONNECTED`, `EXPIRED`, `RATE_LIMITED`, `REAUTH_REQUIRED`,
`DISCONNECTED`. Журнал содержит только request ID, логическую модель, backend,
статус, задержку и token usage. Промпты, ответы, headers и OAuth-ошибки с сырыми
телами провайдеров в журнал не записываются.

## Управление Docker Compose

Все команды выполняются из корня проекта:

```bash
docker compose logs -f gateway
docker compose restart gateway
docker compose down
```

После изменения моделей или маршрутов примените настройки из TUI или перезапустите
`gateway`. `down` сохраняет
том с настройками и аккаунтами. `docker compose down -v` удаляет его вместе
с ключами и авторизацией. Не используйте эту команду для обычной остановки.

`gateway` работает от пользователя с UID 10001. Другие сервисы СПАС в сети
Compose смогут обращаться к `http://gateway:8008` с внутренним ключом Gateway.

## Проверки

После подключения каждого аккаунта выполните независимый запрос в **Главная → Тестирование**. `/health` и healthcheck Compose подтверждают работу HTTP-сервера;
доступ к модели и квоту подписки проверяет именно запрос из TUI.

Для разработки вне контейнера поддерживается Python 3.12+ и uv:

```bash
uv sync --locked --extra dev --extra claude --extra colab
uv run --locked --extra dev --extra colab python -m pytest -q
uv run --locked --extra dev ruff check llm tests
uv run --locked --extra dev ruff format --check llm tests
```

Команду тестов можно запускать без предварительного `uv sync`: uv подготовит
окружение проекта автоматически. Для тестов Colab нужен `--extra colab`;
Claude SDK для этой проверки не требуется. Запускайте pytest через uv либо
`.venv/bin/python -m pytest`, чтобы не использовать системный Python без
зависимостей проекта. Pytest явно проверяет наличие `pytest-asyncio`.

Блокировки используют `flock`, завершение CLI — группы процессов POSIX.
