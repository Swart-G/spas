# Executor MCP

Executor принимает команду и контекст, обращается к Safety Checker, запускает
разрешённую программу в ограниченном Docker-контейнере и возвращает результат.

Быстрый старт, подключение Codex и проверки: [CODEX_SETUP.md](CODEX_SETUP.md).

## Границы задания

Основные требования: ограничение вывода, журналирование, проверки/подключение,
отдельный пользователь и права, Dockerfile и requirements.txt.
Дополнительно к буквальному минимуму реализованы:

- тайм-ауты и удаление оставшихся дочерних процессов — для ограничения исполнения;
- request_id, ротация и скрытие содержимого команд в логах — для диагностики;
- политика точных путей и readonly-папка /inputs — для управляемого доступа к данным;
- одна выполняемая команда с ответом busy — для безопасной очистки общего UID;
- ручная консоль и явный режим разработки без checker — для самостоятельной проверки;
- автоматические регрессии и Docker/MCP smoke-тесты — больше, чем минимальный .md.

Отдельные агенты мониторинга, SSH к нескольким серверам, восстановление сервисов,
память решений и реализация правил Safety Checker в эту работу не входят.
Для Diagnostic Agent добавлены только средства чтения операторских снимков сервисов.
Код и тесты checker взяты из ветки коллеги без изменений для локальной интеграции.

## Контракт и подключение Safety Checker

Инструмент `execute_command`:

```json
{
  "command": ["uname", "-a"],
  "context": {"incident_id": "incident-42", "reason": "Узнать версию ядра"}
}
```

`command` — непустой список непустых строк без NUL. Общая длина с разделителями
не больше 4096 символов. Строка `"uname -a"` больше не принимается по MCP.
В контексте обязательны `incident_id` и `reason`, до 2000 символов каждое.
Контекст объясняет назначение команды, но не выдаёт разрешение на выполнение.

Взяты готовые `checker.py`, `__init__.py`, `shared/contracts/safety.py` и тесты
из коммита [d0c6e4f](https://github.com/Swart-G/spas/commit/d0c6e4f)
ветки `safety-checker/rule-based`. Логика checker перенесена без изменений.
Предыдущий `e73e222` содержал адаптер строк, но более свежий контракт уже argv.

Согласованный интерфейс:

```python
async def check(command: list[str], context: ExecutionContext) -> dict[str, object]:
    # Результат: {"decision": "ALLOW" | "DENY" | "REQUIRE_APPROVAL", "reason": "..."}
    ...
```

Подключение выполняет **Executor**. `configured_server()` вызывает
`load_checker()` и передаёт объект в `create_server(checker=checker)`.
И stdio-сервер, и ручная консоль по умолчанию используют этот путь.
Прямой `create_server()` без checker остаётся закрытым для исполнения.
Ошибка загрузки политики останавливает запуск; перехода в unchecked-режим нет.

Перед проверкой сервер делает неизменяемый снимок `argv = tuple(command)`.
Checker получает отдельный `list(argv)`. При `ALLOW` запускается исходный
снимок: checker не может случайно изменить исполняемую команду через список.
Нет повторного разбора, склейки строки, подстановок или запуска через Bash.
`PATH` задан в коде и не содержит `/workspace`; код и программы образа read-only.

| Ситуация | Результат |
| --- | --- |
| `ALLOW` | Проверка путей и запуск argv под пользователем executor |
| `DENY` | `denied`, процесс не создаётся |
| `REQUIRE_APPROVAL` | `approval_required`, процесс не создаётся |
| Сбой, лишние поля/неверный ответ, отсутствие checker | `error`, процесс не создаётся |
| Проверка дольше 5 секунд | `error`, процесс не создаётся |

Механизм получения человеческого разрешения здесь не реализован. Текст
`reason="approved"` не заменяет разрешение. LLM Safety Analyzer не подключён:
сейчас используется готовая проверка правилами команды проекта.

## Чтение, запись и исполнение

`cwd=/workspace` только задаёт начальную папку. Ограничения обеспечиваются
пользователями, правами файлов, mount-настройками и Docker-профилем.

| Объект | Доступ процесса команды |
| --- | --- |
| Пользователь | UID/GID 10001, дополнительные группы отсутствуют, capabilities = 0 |
| `/workspace` | Начальная папка; чтение/запись; tmpfs 64 МиБ; прямой запуск файлов запрещён (`noexec`) |
| `/inputs` | Опциональные данные оператора; только чтение; в checked-режиме нужны точные разрешённые пути |
| `/app`, ОС образа | Запись запрещена (`--read-only`) |
| `/var/log/executor` | Недоступен пользователю команды; журналы пишет контроллер |
| `/tmp`, `/dev/shm` | Приватные временные каталоги контроллера; командам недоступны |
| Сеть, Docker хоста, папка проекта хоста | Не подключены; только loopback, без Docker socket |

Новые файлы команды получают `600`, каталоги — `700` благодаря `umask=077`.
Сам `/workspace` имеет root:10001 и `770`: контроллер может войти в него перед
сменой UID, а группа executor — работать с файлами. Все команды одного
контейнера работают под одним пользователем и делят эту рабочую папку.
После закрытия контейнера её содержимое удаляется. Это не изоляция между
разными инцидентами внутри одного MCP-сеанса.

Контроллер внутри контейнера работает как root с **только** SETUID, SETGID,
KILL: сменить пользователя дочернего процесса и остановить его потомков.
Процесс команды работает без этих прав. `no-new-privileges` запрещает повышение
прав через setuid. Стандартные seccomp/AppArmor Docker не отключаются.
Дополнительно установлены 1 CPU, 256 МиБ памяти, 128 процессов, лимит файла
16 МиБ и ограничение числа открытых файлов. Это общий бюджет контейнера.

`Execution_policy.py` отказывает в исполнении без ожидаемых прав и mount-флагов.
Локального исполнения команд на хосте нет. Образ запускается через
`Run_docker.sh`: обычный `docker run IMAGE` не задаёт обязательный профиль.
Проверки Python страхуют от части ошибок запуска; границей изоляции является
сам Docker, а не маркер `/etc/spas-executor`. Оператор Docker — доверенный.

В checked-режиме разрешены `pwd`, поддержанные флаги `uname`, чтение/список
явно разрешённых ресурсов. По умолчанию доступны `ls /workspace` и `ls /inputs`.
`cat` требует настройки конкретного файла. Читать можно только `/inputs`,
а `/workspace` разрешён только для списка каталога. Симлинки в пути и
спецфайлы отклоняются. Каталог на стороне хоста нельзя менять во время запроса:
`lstat` не обеспечивает атомарную защиту от гонки с администратором хоста.

Docker-команды дополнительно запрещены политикой этого развёртывания, хотя
checker умеет их проверять. Docker CLI/socket и доступ к серверу хоста не
предоставляются. Управление контейнерами homelab потребует отдельного
ограниченного канала, а не подключения всего Docker socket.

`--without-safety` — явный режим разработки для доверенного оператора.
Права Docker остаются, но правила checker отключаются. `noexec` не мешает
интерпретатору читать текст скрипта; в обычном режиме интерпретаторы запрещает
checker. Режим без проверки не следует подключать к автономной LLM.

## Вывод и тайм-аут

`Runner.py` читает stdout и stderr одновременно, порциями по 4096 байтов.
Сохраняет максимум **8192 байта каждого потока**; остаток считывает и отбрасывает,
чтобы заполненная труба не остановила процесс. Полный вывод не накапливается.

UTF-8 не разрезается посередине корректного символа. Неверные байты заменяются
на `�`, после чего текст при необходимости снова ограничивается до 8192 байтов.
`stdout_truncated` и `stderr_truncated` сообщают об усечении. Это лимит байтов
вывода, не токенов и не полного JSON: MCP отдаёт текстовую и структурированную
формы результата. Усечение не меняет exit_code.

Команда получает 30 секунд. При завершении, тайм-ауте или отмене запроса Runner
убирает все оставшиеся процессы UID 10001, в том числе потомков, вызвавших
`setsid()`. Фоновые задания между вызовами не поддерживаются. Сигналы по `pidfd`
защищают от переиспользования номера процесса. Отмена во время создания процесса
не теряет ссылку на него, повторная отмена не прерывает очистку.

Очистка ограничена тремя секундами. Если она не завершается или выдаёт ошибку,
контроллер пишет `process_cleanup_failed` и завершает контейнер: неизвестные
процессы не переходят к следующему запросу. Docker удаляет его PID namespace.
Для этого требуется Linux с поддержкой `pidfd_open` (ядро 5.3+).

Поскольку все команды используют один UID, исполняется только одна команда
за раз. Сервер занимает слот ещё до вызова checker: параллельный запрос получает
`error` с сообщением `Executor is busy`, `safety_checked=false` и свой request_id.
Checker повторно не вызывается; клиент может повторить запрос позже. Очередь
ожидания не создаётся. Отмена или ошибка освобождает слот после очистки процесса.
Отдельная блокировка Runner остаётся защитой при прямом вызове из Python.

Ошибки валидации SDK заменяются коротким сообщением с request_id, без копирования
отвергнутого ввода. Поле reason ответа Safety Checker ограничено 2000 символами;
ответ с превышением лимита не допускает запуска.

Результат: `stdout`, `stderr`, `exit_code`, `status`, `error`, признаки усечения,
`safety_checked`, `request_id`. У незапущенной команды exit_code равен `null`.

## Как работает логирование

1. `setup_logging()` создаёт обработчик stderr и отдельный файл с ротацией.
2. На входе в `call_tool` сервер создаёт `request_id` и кладёт его в `ContextVar`.
   Асинхронные запросы имеют независимые контексты.
3. Сервер пишет события валидации/проверки; Runner — запуска, тайм-аута и завершения.
4. `finally` пишет `request_finished` даже при отказе, исключении или отмене.
5. Тот же request_id возвращается клиенту для поиска всех событий запроса.

Одна строка журнала — JSON с временем UTC, уровнем, событием, PID и техническими
полями. `incident_ref` — короткий SHA-256 от incident_id для поиска; не шифрование.
Команда, reason, исходный incident_id, stdout/stderr, текст исключения и локальные
переменные в журнал не попадают. Стек содержит тип исключения, файл, функцию,
номер строки: до 12 кадров каждого из максимум трёх исключений. Вложенные
`ExceptionGroup` разворачиваются до конкретных причин, без их сообщений.

Сообщения `mcp.*` также проходят через журнал Executor: событие `mcp_sdk_event`
сохраняет уровень, `sdk_component` и безопасный стек. Исходные msg/args SDK
не копируются: в них могут оказаться присланное имя инструмента и отвергнутые
данные. Повторная настройка не дублирует записи, shutdown возвращает прежние
обработчики `mcp`. Обработчики root и других библиотек Executor не меняет.

Основные события: `request_received`, `command_validated`, `safety_check_started`,
`safety_decision`, `read_scope_rejected`, `execution_policy_failed`,
`process_started`, `process_finished`, `process_timeout`, `process_cancelled`,
`execution_busy`, `request_busy`, `mcp_sdk_event`, `process_cleanup_failed`, `request_finished`.
Также журналируются ошибки, отмены и старт/остановка сервера/ручной консоли.

stderr используется для журнала, stdout MCP — для протокола. Ручная консоль
показывает результат в stdout, экранируя управляющие символы терминала и bidi.
Это защищает отображение от содержимого читаемых файлов; исходный вывод MCP
не меняется. В Docker файлы находятся в named volume
`spas-executor-logs`: `<container-hostname>/server-<PID>.log`. Разные контейнеры
не конфликтуют даже с одинаковыми PID. Каталог — `700`, файл — `600`.
На файл: 2 МиБ, три резервные копии. Отдельно ограничен собственный журнал
Docker: драйвер `local`, файлы по 2 МиБ, максимум три файла. Старые каталоги контейнеров автоматически
не удаляются; срок хранения должен задать оператор.

При недоступности файла журнал продолжает работать через stderr. Отказ записи
файла сообщается один раз. Если оба канала недоступны, либо процесс убит SIGKILL,
гарантии сохранения последних событий нет. Повторная настройка не дублирует
обработчики. Протокольные ошибки до `call_tool` обрабатывает MCP SDK; его
диагностические записи очищаются тем же мостом журналирования.

## Инструменты для Diagnostic Agent

`get_service_logs`, `get_service_state` и `check_service_availability` принимают
имя сервиса и тот же `context` с `incident_id` и `reason`. Только для логов
доступен дополнительный параметр `lines` (1–200, по умолчанию 100).

```json
{"service":"gateway","context":{"incident_id":"incident-42","reason":"Проверить сбой"},"lines":50}
```

У всех трёх инструментов один формат ответа: `status`, `kind`, `service`,
`output`, `truncated`, `observed_at`, `error`, `request_id`. `kind` равен
`logs`, `state` или `availability`. `state` возвращает `running`, `stopped`
или `unknown`; доступность — `available`, `unavailable` или `unknown`.
Доступность означает результат Docker healthcheck. Если healthcheck не задан,
запущенный контейнер имеет доступность `unknown`: сам факт запуска не доказывает,
что сервис принимает запросы. Остановленный контейнер — `unavailable`.

Executor по-прежнему работает в контейнере без сети и Docker socket. На хосте
оператор запускает `Diagnostic_collector.py` из корня репозитория в Python-окружении
с установленным `requirements.txt`: он читает Docker **только для
сервисов, перечисленных в конфигурации**, и атомарно записывает небольшие
снимки в папку, которую Executor получает через существующий readonly mount
`EXECUTOR_INPUTS_DIR`. Например, если фактическое имя контейнера Gateway —
`spas-gateway-1`:

```sh
umask 077
install -d -m 0750 /tmp/spas-diagnostic-inputs
install -d -m 0750 /tmp/spas-diagnostic-inputs/diagnostics
install -d -m 0700 /tmp/spas-diagnostic-config
printf '%s\n' '{"services":{"gateway":"spas-gateway-1"}}' > /tmp/spas-diagnostic-config/services.json
python3 -m executer.server_mcp.Diagnostic_collector \
  --config /tmp/spas-diagnostic-config/services.json \
  --output /tmp/spas-diagnostic-inputs/diagnostics --watch
```

Сборщик требует установленный Docker CLI и права оператора на просмотр
указанных контейнеров. Запустите его в отдельном терминале. При подключении
MCP задайте `EXECUTOR_INPUTS_DIR=/tmp/spas-diagnostic-inputs` для
`Run_docker.sh`. Имя контейнера уточните через `docker ps` и храните список
разрешённых сервисов вне каталога, доступного Executor.

Каталоги снимков должны принадлежать пользователю сборщика и его основной
группе: права `0750`; файлы получают `0640`. Скрипт запуска добавляет эту группу
только контроллеру MCP; выполняемые команды работают без дополнительных групп.
UID пользователя и GID группы не должны быть `10001` — это идентификаторы
выполняемых команд. Совпадение UID даёт доступ по правам владельца даже после
сброса дополнительных групп; сборщик, запуск и чтение снимков его запрещают. Если каталог
создан другим пользователем, является симлинком или открыт для остальных,
сборщик откажется запускаться. При изменении списка сервисов перезапустите
сборщик: прежние снимки удаляются до публикации новых.
Используйте отдельную группу оператора без посторонних пользователей;
расширенные ACL на каталогах и файлах диагностики не допускаются.
Конфигурация должна находиться в доверенном каталоге, принадлежать оператору
и иметь права `0600`; сборщик проверяет это до обращения к Docker.
Если остались каталоги снимков от прежнего запуска с более открытыми правами,
исправьте их права или удалите старые снимки перед перезапуском сборщика.

Сборщик опрашивает до восьми сервисов одновременно и после полного обхода
ждёт 30 секунд перед следующим. Из Docker inspect он берёт только признак
запуска и статус healthcheck, не всю историю проверок. Если данные старше 120 секунд,
инструмент возвращает ошибку вместо устаревшего состояния. Максимум снимка —
32 КиБ; логов — 8192 байт в JSON-представлении, до 200 строк; чтение идёт только из файлов
`/inputs/diagnostics/<service>/snapshot.json` без симлинков. Произвольные
пути, URL, имя контейнера или команды MCP-клиент задать не может. Логи могут
содержать секреты сервиса: оператор должен разрешать только те контейнеры,
чьи журналы допустимо передавать Diagnostic Agent. Safety Checker и контракт
`execute_command` не меняются.
