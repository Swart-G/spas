# SAFETY CHECKER

Rule-based слой проверки команд перед Tools в существующем конвейере
Executor MCP → Safety Checker → Tools. Python 3.10+, только стандартная библиотека.
Модуль ничего не исполняет и не обращается к LLM. Analyzer и Audit Log остаются
отдельной зоной Ярослава. Синхронное ядро используется локально; асинхронный
`ExecutorSafetyChecker` совместим с Executor в ветке `workeragent/executermcp`
(проверено на коммите `79f4fd09fcc24a4ae0e49235e42db2d3adfe67bd`). Код этой ветки
не копируется в реализацию checker. Подтверждение общего контракта командой
остаётся шагом ревью; техническая совместимость проверена тестами.

## Контракт

`shared/contracts/safety.py`:

- `CommandRequest(command: str)` — одна команда;
- `SafetyResult` — `decision`, `risk`, стабильный `rule_id`, `reason`, разобранный
  неизменяемый `argv`;
- `result.allowed` истинно **только** для `ALLOW`;
- `ExecutionContextPort` — объект с полями `incident_id` и `reason`;
- `ExecutorSafetyDecision` — словарь ровно с `decision` и `reason`;
- `ExecutorSafetyCheckerPort` — `async check(command, context)`.

Executor передаёт свой Pydantic `ExecutionContext` напрямую: наследование от
`ExecutionContextPort` не требуется, проверяется структура объекта. Обе строки
должны быть непустыми, длиной не более 2000. Некорректный контекст → DENY.
Контекст не задаёт права, политику или подтверждение пользователя.

Внутренний `SafetyResult` сохраняет риск, код правила и argv для дальнейшего
анализа/аудита. Адаптер возвращает только два поля: текущий `SafetyDecision`
Executor запрещает дополнительные поля (`extra='forbid'`). Его не нужно менять.

Риск — оценка правила, а не вероятность и не полная оценка конкретного инцидента.

| Риск | Смысл в MVP | Решение |
|---|---|---|
| LOW | Поддерживаемое чтение в заданной области | ALLOW |
| MEDIUM | Перезапуск разрешённого контейнера | REQUIRE_APPROVAL |
| HIGH | Неизвестная команда/аргументы | REQUIRE_APPROVAL |
| HIGH | Ошибка ввода, shell-синтаксис, выход за область доступа | DENY |
| CRITICAL | Явно запрещённые операции и средства произвольного исполнения | DENY |

## Правила и приоритет

1. Невалидный запрос, пустая строка, длина >4096, незакрытые кавычки → DENY.
2. Операторы shell, подстановки, wildcard, комментарии, escape-последовательности,
   управляющие и не-ASCII символы → DENY. Запрещены даже внутри кавычек.
   Это ограниченная грамматика MVP, а не интерпретатор shell.
3. Встроенный denylist и дополнительные `denied_executables` приоритетнее допуска.
   Запрещены в том числе удаление, запись через cp/mv/tee, изменение прав,
   sudo/env/xargs/find, оболочки и основные интерпретаторы.
   Абсолютные пути к запрещённым программам также распознаются. Остальные пути
   к исполняемым файлам и присваивания окружения не поддерживаются.
4. Допуск только по полной форме команды, аргументам и точному ресурсу.
5. Для Docker все формы вне явно поддерживаемого списка → DENY, включая
   неизвестные подкоманды, плагины и неподдерживаемые флаги. Глобальные опции
   перед подкомандой (`--debug`, `-D`, `--context`, `-H`, `--config` и другие)
   запрещены: они не могут скрыть запрещённое действие за запросом подтверждения.
   Флаги после подкоманды также не допускаются вне её точной разрешённой формы.
6. Остальные команды (кроме Docker) требуют подтверждения. Denylist не претендует
   на перечисление всех опасных программ: защита автоматического запуска — allowlist.

| Команда | Условия / решение |
|---|---|
| `pwd` | Без аргументов → ALLOW |
| `uname` | Без аргументов или только `-a -s -r -m -n -v` → ALLOW |
| `ls -lah /srv/spas/logs` | Явные пути из `readable_paths`; ограниченный набор флагов → ALLOW |
| `cat /srv/spas/app.log` | Все пути в `readable_paths`, без флагов → ALLOW |
| `docker ps`, `docker ps -a`, `docker ps --all` | Только эти формы → ALLOW |
| `docker logs --tail 100 -- backend` | 1–1000 строк, контейнер в `containers` → ALLOW |
| `docker restart -- backend` | Один контейнер в `containers` → REQUIRE_APPROVAL |
| `curl ...` | Нет правила допуска → REQUIRE_APPROVAL |
| `docker --debug exec backend id`, `docker -D ps` | Глобальные опции Docker → DENY |
| `docker inspect backend`, `docker ps --debug`, `docker custom-plugin ...` | Неподдерживаемые формы Docker → DENY |
| `rm ...`, `docker exec ...`, `docker debug ...`, `docker volume ...` | DENY |
| `ls`, `cat /etc/shadow`, `pwd && uname` | DENY |

Флаги `ls`: `-l -a -h -la -al -lh -lah -alh`, перед путями.
Пути сравниваются целиком: разрешение каталога не даёт разрешения читать его файлы
через `cat`. Чтение текущего каталога через неявный `ls` запрещено.
Кавычки поддерживают пробелы в явно разрешённых путях. Неизвестные флаги
не становятся автоматически безопасными.

## Пример (ничего не запускает)

```python
from executer.safety_checker import RuleBasedSafetyChecker, SafetyPolicy
from shared.contracts.safety import CommandRequest

checker = RuleBasedSafetyChecker(SafetyPolicy(
    readable_paths=frozenset({"/srv/spas/app.log", "/srv/spas/logs"}),
    containers=frozenset({"backend"}),
))
result = checker.check(CommandRequest("docker logs --tail 100 -- backend"))
assert result.allowed
assert result.argv == ("docker", "logs", "--tail", "100", "--", "backend")
```

По умолчанию списки файлов и контейнеров пусты. Политику задаёт доверенная
конфигурация оператора, не Worker/LLM. Добавление пути или контейнера означает
осознанное разрешение читать его содержимое/логи: там могут быть секреты.

## Асинхронное подключение к существующему Executor MCP

После объединения компонентов в одном checkout:

```python
from executer.safety_checker import ExecutorSafetyChecker, RuleBasedSafetyChecker, SafetyPolicy
from executer.server_mcp.Server import create_server

rules = RuleBasedSafetyChecker(SafetyPolicy(containers=frozenset({"backend"})))
checker = ExecutorSafetyChecker(rules)
server = create_server(checker=checker)
# server.run(transport="stdio") — запуск только в подготовленном окружении.
```

Executor использует `await checker.check(command, context)`. Синхронный вызов
`rules.check(CommandRequest(...))` сохранён. Асинхронный метод выполняет только
короткую ограниченную проверку (команда <=4096 символов), без сети, процессов и
файлового I/O; отдельные потоки и event loop не создаются. Ошибка ядра передаётся
Executor, который уже прекращает выполнение при ошибке или тайм-ауте checker.

`asyncio.run()` внутри Executor не нужен. Нельзя передавать `rules` вместо адаптера:
у него другой синхронный интерфейс. MCP-режим `without-safety` для этого подключения
не используется. Python самого checker — 3.10+, существующего Executor — 3.12+.

Текущий `Runner.py` Семёна запускает исходную строку через `bash -c`. Адаптер
устраняет несовместимость интерфейсов, но не изменяет Runner. Поэтому до реального
исполнения остаются ограничения ниже; успех интеграционных тестов с заглушкой
не означает готовность shell-пути для production.

## Что остаётся для полного исполнения через Executor MCP

- Проверять каждое действие непосредственно перед запуском, включая повторные
  попытки. Проверка одной команды не разрешает весь план. Ошибка checker → запрет.
- При `ALLOW` исполнять **ровно** `result.argv` без shell, с фиксированным отображением
  имён программ на доверенные абсолютные пути. Не использовать исходную строку
  для `shell=True`, `sh -c`, SSH-оболочки или повторного разбора.
- Зафиксировать рабочий каталог, окружение, пользователя и Docker endpoint.
  Не принимать PATH, DOCKER_HOST, DOCKER_CONTEXT, DOCKER_CONFIG и подобные параметры
  от агента. Ограничить время и объём вывода; `--tail` не ограничивает размер строки.
- Обеспечить отдельную авторизацию роли агента: Diagnostic не должен получать право
  на изменение состояния или чтение чувствительных данных даже после approval.
- Проверять реальные объекты файловой системы, ссылки и права доступа; этот модуль
  сравнивает только имена. Защититься от подмены файла/ссылки между проверкой и чтением
  изоляцией/правами либо отдельным безопасным инструментом чтения.
- `DENY` завершает запрос. Analyzer не может превратить запрет в допуск.
  `REQUIRE_APPROVAL` останавливает запуск: отдельный доверенный процесс должен
  привязать подтверждение к точному argv, пользователю, окружению и версии политики,
  затем повторно проверить актуальные ограничения. Поля `approved=true` от LLM недостаточно.
  Неизвестные команды требуют отдельной проверки человеком; HIGH не обещает безопасность.
- Передавать решение и результат исполнения в Audit Log; не сохранять секреты
  без фильтрации. Сам журнал и LLM Analyzer здесь не реализованы.

В ветке checker поставляются правила и адаптер. Полное соединение компонентов,
фиксированное окружение и изменение Runner выполняются при интеграции с Семёном;
библиотека принятия решений сама по себе не является sandbox.

## Проверки

Из корня репозитория:

```sh
python3 -m unittest discover -s tests -v
```

Без кода Executor доступны 27 тестов правил и адаптера. Ещё 6 интеграционных тестов
автоматически пропускаются до появления `executer/server_mcp/Server.py` и зависимостей
из `Requirements-executor.txt`. В собранном checkout с обеими компонентами и этими
зависимостями та же команда запускает все 33 теста. Для отдельного checkout Executor
можно добавить его корень в `PYTHONPATH` вместе с корнем checker.

Тесты не запускают инфраструктурные команды. Проверяются допуск, риски, приоритет
запретов, аргументы, границы путей/контейнеров, shell-обходы, глобальные флаги Docker,
невалидные запросы и совместимость sync/async. Интеграционные тесты вызывают настоящий
MCP-инструмент через `server.call_tool` и настоящий Pydantic-валидатор ответа;
только `run_shell` заменяется `AsyncMock`. Проверено: ALLOW передаёт одну команду,
DENY/REQUIRE_APPROVAL/ошибка/отсутствие checker не вызывают исполнителя.

Линтер: правила Ruff из `origin/main:pyproject.toml` (E, F, I, UP, B, ASYNC),
с проверкой совместимости синтаксиса checker с Python 3.10.
