# Safety Analyzer: контрольная оценка quality-v1

Дата: 2026-10-22. Ветка: `safety-checker/-safety-analyzer`.
Машинный результат и хеши: [quality-v1-controls.json](quality-v1-controls.json).

Проверена система оценки. Качество и стабильность **реальной Nimble не измерены**.
Контрольные провайдеры намеренно выдают ошибочные ответы и не читают метки набора.

## Набор и метод

90 синтетических кейсов: safe/dangerous/ambiguous — по 30. Development содержит
60 кейсов, holdout — 30; все варианты одного семейства остаются в одном split.
70 кейсов проходят правила и требуют модели, включая 20 опасных и 20 неоднозначных.
Ещё 10 запретов и 10 обязательных подтверждений проверяют приоритет правил.
Разметка предварительная, без независимой проверки; holdout составлен тем же автором.

Для каждого профиля: пять полных перемешанных проходов, seed=42, 450 анализов,
350 ожидаемых обращений к модельному адаптеру. Проверены `chat_completions`
и `decisions`: восемь прогонов, всего 3600 анализов и 2800 обращений к mock-провайдеру.
Команды не выполнялись. Исходные контексты и секреты в отчёт не записываются.

## Результат контролей

Оба протокола дали одинаковые показатели. Нестабильность ниже указана по всем
90 кейсам; 20 решений правил остаются стабильными.

| Профиль | Model false allow | Общая false allow | False block | Ошибки | Нестабильные кейсы | Gate |
|---|---:|---:|---:|---:|---:|---|
| always-allow | 100% | 66.67% | 0% | 0% | 0% | FAIL |
| always-deny | 0% | 0% | 100% | 0% | 0% | FAIL |
| alternating | 60% | 40% | 40% | 0% | 77.78% | FAIL |
| unavailable | 0% | 0% | 100% | 77.78% | 0% | FAIL |

`always-allow` даёт по 100 ошибочных разрешений опасных и неоднозначных действий
за прогон профиля. `alternating` меняет решение на каждом повторе одного snapshot:
нестабильны все 70 модельных кейсов, у 40 ограниченных кейсов есть переходы ALLOW ↔ DENY.
У `unavailable` model coverage =0%; fail-closed DENY не засчитываются как правильные
классификации. Обходов и расхождений правил во всех восьми прогонах — 0.

Все намеренные дефекты обнаружены; harness завершился успешно, quality gates
профилей провалились ожидаемо. Пороги применяются также отдельно к holdout.
Unit-тест проверяет, что ошибки holdout не скрываются хорошим development.

## Проверки реализации

`pytest -q`: **360 passed, 2 skipped** (live-тесты).
Ruff check и format check прошли. `scripts/dev.py --smoke` подтвердил запуск
и функциональный запрос через локальную заглушку.
Интеграционные тесты прошли через закреплённый настоящий код SPAS Gateway,
включая System One → native Nimble преобразование и все три решения;
удалённый inference в этих тестах подменён.

## Реальная модель

В репозитории реализован `bespokelabs/Bespoke-Nimble-9B`, официальный scorer
`dcfdbd9a64f0d869f658d7a72f1beaee32737773`. В текущей среде нет CUDA-устройств
и torch; `SAFETY_GATEWAY_BASE_URL`, `SAFETY_GATEWAY_API_KEY`, `SAFETY_MODEL` не заданы.
Runtime не развёрнут, веса не загружались. Статус модельного benchmark: **not_run**.

Для продолжения нужен работающий GPU runtime через существующий Gateway;
Analyzer уже поддерживает `SAFETY_COMMAND_API=decisions`.
Команды запуска и состав отчётов: [evaluation.md](../evaluation.md).
Для сравнения закрепите веса, scorer и один backend маршрута.

Даже 0 false allow на 20 модельных опасных кейсах дали бы верхнюю границу
95% Wilson около 16.1% для доли кейсов с хотя бы одной ошибкой за пять повторов.
Повторы не являются независимыми кейсами; синтетический набор не описывает
распределение production-запросов. Контрольные результаты выше не заменяют benchmark весов.
